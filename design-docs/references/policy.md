# 参考資料: 設計ドキュメント方針（判断基準の抜粋）

`SKILL.md` の手順で判断に迷ったときだけ読む。方針の全体像ではなく、判断に必要な部分だけを載せている。

## 1. 「前提 / 何を / どう」の3段階

設計ドキュメントを分ける根底の切り分け。

| 段階 | 決めること | ファイル |
| :--- | :--- | :--- |
| 前提 | 目的、課題、利用者、制約、非機能 | `requirements.md` |
| 何を作るか | 実現すべき機能・画面・データの具体像 | `specification.md` |
| どう作るか（方針） | 全体構成、技術選定、共通規約、境界 | `architecture.md` |
| どう作るか（詳細） | モジュール構成、処理詳細、状態遷移 | `design.md` |

この線は「顧客が理解できるかどうか」で引いた線と一致する。

- 前提・何を作るか → 顧客と合意する粒度。専門用語を避け、実現する機能・画面・データの単位で書く
- どう作るか → 顧客が理解できなくてよい

**「仕様書」という語は業界で意味が固まっていない。** 本方針は `specification.md` を「何を作るか」に置く立場を採る。プロジェクト内でこの意味を共有してから使う。

## 2. 4ファイルの役割分担

| ファイル | 主な読み手 | 更新頻度 |
| :--- | :--- | :--- |
| `requirements.md` | 全員（顧客含む） | 要件が変わったとき |
| `specification.md` | 全員（顧客含む） | 機能・画面・データが変わったとき |
| `architecture.md` | 開発者・AI エージェント（**常時**） | 低い。年に数回見直す程度 |
| `design.md` | 開発者・AI エージェント（機能ごと） | 高い。コードと一緒に動く |

`specification.md` は **機能一覧がハブ**。ここから画面・データ・外部連携が枝分かれする。機能一覧が甘いと下流がすべてぶれる。

## 3. architecture.md を分離する理由

**理由1：更新頻度が決定的に違う。** これが最大の理由。`architecture.md` は頻繁に変わらない内容だけを含める。一方 `design.md` は機能を足しても、リファクタリングでも変わる。同じファイルに置くと「頻繁に変わる部分」に引きずられて「変わらないはずの部分」まで差分が出て、レビューの焦点がぼやける。

**理由2：レイヤーの役割が違う。** `architecture.md` の価値はモジュール間の関係を示すコードマップ、アーキテクチャ上の不変条件、レイヤーやシステム間の境界を明示する点にある。特に重要な不変条件は「何かが存在しないこと」として表現されることが多く、コードを読むだけでは把握しづらい。詳細設計とは性質の異なる情報であり、混ぜるべきではない。

**理由3：AI エージェントに渡す単位として最適。** `architecture.md` は常時読ませたい情報（always-on）、`design.md` は着手する機能に応じて読ませたい情報（on-demand）。1ファイルにまとまっているとこの出し分けができない。だから `AGENTS.md` からは `architecture.md` を参照させ、`design.md` は作業時に個別指定する。

**理由4：ADR の置き場所になる。** 技術選定の理由は「変わらないが、後から必ず参照される」情報。

## 4. 更新頻度による切り分けの原則

情報をどのファイルに置くか迷ったら、**その情報がどれくらいの頻度で変わるか**で決める。読み手や話題の近さではない。

- コードを変えるたびに変わる → `design.md`
- 年に数回しか変わらない → `architecture.md`
- 顧客との合意が変わったときだけ変わる → `requirements.md` / `specification.md`
- 実装のたびに変わる → **そもそも文書に書かない**（その情報はコードだけにある）。文書に書いたこととコードが食い違ったときは、下の「文書を正とする」に従う

**更新されない設計ドキュメントは「間違った地図」になり、いずれ害になる。** 維持できない粒度で書くくらいなら書かない。

**ADR は決定の履歴を追記で残す。** 決定変更と書式統一を区別する。詳細は「ADR の記録と改定」に従う。

**二重管理を避ける。** コード・区分の定義はデータモデルの項目定義に吸収する。独立した一覧を作らない。

**文書とコードが食い違ったら、文書を正とする。** 利用者は文書で確認し、コードはあまり読まない。食い違いはコードの不具合とみなし、文書に合わせてコードを直す。文書を変えるのは、人が仕様の変更として決めたときだけ。

**設計が先行する箇所には印を付ける。** Issue から設計して、まだコードに無い箇所には `（未実装 #<番号>）` を付ける。印のある箇所の食い違いは、まだ実装していないだけで不具合ではない。印は実装を終えた時点で外す。

### ADR の記録と改定

`architecture.md` の「技術選定と理由（ADR）」に、次の6項目をこの名称・順序で記録する。

| 項目 | 見出し | 記載内容 |
| :--- | :--- | :--- |
| タイトル（Title） | レベル3: `ADR-001: タイトル` | 固定番号と決定を識別できるタイトル |
| ステータス（Status） | レベル4 | `Accepted` / `Proposed` / `Suspended` のいずれか |
| 意思決定内容（Decision） | レベル4 | 何を決めたか |
| 背景（Context） | レベル4 | 決定が必要になった背景 |
| 影響（Consequences） | レベル4 | 技術的負債、トレードオフ、維持・運用への影響 |
| 他に検討したもの（Alternatives Considered） | レベル4 | 比較した候補と選ばなかった理由 |

- 番号は `ADR-001` から始める。既存番号の最大値の次を採番し、欠番を詰めず、再採番・再利用しない。999を超えたら桁を増やす。
- Statusは実装状況と合意を確認して選ぶ。受け入れ済みは `Accepted`、提案・検討中は `Proposed`、保留・中断は `Suspended`。実装済みというだけで合意済みと推測しない。確認できなければ `TBD` とし、確認事項として提示する。
- 背景・影響・比較案が不明なら `TBD` とし、不足情報を PR本文の確認事項に記載する。「比較していない」と確認できた場合はその事実を書く。比較履歴が不明な場合に「比較案なし」と断定しない。
- 決定を変更する場合は新しい番号のADRを追記する。旧ADRに新ADRへの参照、新ADRに旧ADRへの参照を加え、旧決定とその理由は保持する。参照は該当見出しへのリンクか、固定番号で明示する。
- 既存ADRの書式統一を求められた場合は、既存番号と決定内容を保って該当箇所だけ整形する。番号が無い記録には未使用の次番号を付ける。不明な項目は創作しない。これは追記原則に対する書式だけの例外であり、決定内容やStatusを根拠なく変更する許可ではない。大きな構成変更は変更案として PRの差分で確認する。未承認の決定変更は既存の決定を保って `Proposed` の新規ADRとして提出し、承認済みと扱わない。

## 5. テストの扱い

更新頻度に従って分散させる（案A）。テスト専用の文書は作らない。

| 中身 | 置き場所 |
| :--- | :--- |
| 合格基準（受け入れ基準） | `requirements.md` の機能要件に併記 |
| 入力から結果が決まる規則（業務ルール） | `specification.md` の業務ルールに入力と期待結果の表で |
| テスト方針、使用ツール、カバレッジ基準、CI での実行 | `architecture.md` の非機能の実現方式 |
| 機能ごとのテスト観点 | `design.md` |
| テストケース・手順 | **テストコード**（文書化しない） |
| 体制・スケジュール | 設計ドキュメントの範囲外 |

**業務ルールの表はテストケースではない。** どの入力でどの結果になるかという仕様（顧客と合意する規則）であり、テストの手順やデータの網羅ではない。テストはこの表の行を写して書く。

**テストケースそのものは規模にかかわらず文書に書かない。** 静的なテスト文書は「ある瞬間のスナップショット」に過ぎず、書き終わった瞬間から陳腐化が始まる。テストコードは実行可能なので嘘をつけないが、文書のテストケースは嘘をつける。**テストコードを正とする**のが原則。

例外的に `test-strategy.md` を切り出すのは、テスト方針の記述量が増えて `architecture.md` を圧迫し始めたとき、または複数ベンダーでの分担・外部委託・監査対応・契約上の納品物が絡むとき。個人開発・小規模開発では該当しない。

## 6. UML のどの図をどこで使うか

★＝その項目の主役級。★なしは補助。

| ファイル | 設計項目 | 図 |
| :--- | :--- | :--- |
| `requirements.md` | 機能要件（システムの範囲） | ユースケース図 ★ |
| `requirements.md` | 業務フロー | アクティビティ図（スイムレーン付き） |
| `specification.md` | 画面遷移 | ステートマシン図 ★ / 画面遷移図 |
| `specification.md` | データモデル | **ER 図** ★（UML 外） |
| `specification.md` | 外部連携 | シーケンス図 |
| `architecture.md` | 全体構成・インフラ | 配置図 ★ / コンポーネント図 |
| `architecture.md` | レイヤー構成・依存の方向 | パッケージ図 |
| `design.md` | モジュール・クラス構成 | **クラス図** ★ |
| `design.md` | 処理詳細 | **シーケンス図** ★ |
| `design.md` | 状態遷移 | **ステートマシン図** ★ |

**図を描かない領域を押さえておく。** 非機能要件、CRUD、メッセージ定義、ADR、共通規約はすべて表かテキストが最適で、UML の出番がない。設計ドキュメントのかなりの部分は UML の外側にある。

**運用方針**

- 5つの図（クラス図・ユースケース図・アクティビティ図・ステートマシン図・シーケンス図）を毎回フルで描かない。案件ごとに濃淡をつける
- その設計で **一番リスクや迷いがある観点** を選んで描く。状態が複雑ならステートマシン図を厚めに
- 使い方は「スケッチ」。伝わることを重視し、属性・メソッドまで正確に書き込むのは必要な箇所のみ
- コミュニケーション図・相互作用概要図は不要（シーケンス図／アクティビティ図と情報量が同じ）
