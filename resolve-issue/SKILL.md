# resolve-issue Skill

## 概要

1つのIssueを1つのPRで、設計してから実装します。PRは2段階で育て、**段階ごとに別のセッションで実行します**（設計者と実装者を分けるため）。

Issue 単位の要件定義はこのスキルの範囲外です。Issue の受入条件は、`create-issue` で要件定義として決めてあるものとして読みます。段階1では、その要件をもとに設計ドキュメントに落とし込みます（`requirements.md` へのシステム全体の要件としての組み直しを含む）。

| 段階 | PRの状態 | 中身 | 人が見るもの |
| :--- | :--- | :--- | :--- |
| 1. 設計 | Draft | 設計ドキュメントの差分、要件の抜けの洗い出し | 設計ドキュメントの差分と、要件の抜け・`？` の行 |
| 2. 実装 | Ready for review | テストと実装（TDD）、品質ゲート | PRの差分、受入条件を参考にしたUAT |

- **正本は Issue の受入条件です。** テストはその写しで、設計ドキュメントはAIが実装を間違えないための補助です。どちらも合意の対象ではありません。受入条件はこのスキルの判断では書き換えません。
- 段階2のセッションは段階1の会話を持ちません。段階1で決めたことは **すべて設計ドキュメントと PR に書き残します**（次節「書き残す先」）。`PLAN.md` のような作業用のファイルは作りません。
- 段階2へ進む合図は、人がセッションを作り直す（または `/clear` する）ことと、同じIssueでこのスキルを呼び直すことです。

## 書き残す先

セッションを作り直すと、会話の中だけにあった考えは失われます。次のセッションや後から読む人に必要な考え・暗黙知・調査結果は、生じたその段階で書き残します。

**まず、設計ドキュメントに残すべき情報かを考えます。**

- 設計ドキュメントに残すべき情報（要件の背景、仕様、設計の判断とその理由、制約など）は、どの段階で生じても `design-docs` で設計ドキュメントに直接書く。書くときは、Issue のコメント（起票時や起票後の要件の議論で書かれたもの）も拾って反映する。
- 設計ドキュメントに残すべきでない情報（デバッグ中の CI の結果など）は、PR コメントに書く。
- 設計ドキュメントが無いリポジトリでは、このスキルのために作らない。設計ドキュメントに残すべき情報も、PR本文か PR コメントに書く。
- Issue は読むだけで、直接書かない。Issue 本文とコメント（要件の調査結果や経緯、`？` の行への答えなど）は要件定義の側で書くもの。要件の抜けへの答えや受入条件の変更を Issue に反映するときは、`create-issue` の「起票後に要件を補う」に従う。

| 残す先 | 残すもの |
| :--- | :--- |
| Issue 本文・コメント | 要件（`create-issue` で書く。このスキルは読む） |
| 設計ドキュメント | 設計ドキュメントに残すべき情報（Issue コメントから拾ったものを含む） |
| PR本文 | PRの概要、レビューしてほしい設計判断、動作確認、段階2の実装者が最初に知る必要のあることの要点 |
| PR コメント | 設計ドキュメントに残すべきでない情報（デバッグ中の CI の結果など） |

- 残すのは、次に読む人が会話を持たずに困るものに限る。作業の実況や、コードやコミットを読めば分かることは書かない。
- 同じ話題の PR コメント（方針の決定など）の内容が変わったら、新しいコメントを足さず、既存のコメントを書き換える（`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...`）。PR本文も最新に保つ。古い決定が並ぶと、次に読む人が迷うため。ただし、コードへの指摘へのリプライと、人に判断を問うコメントは新しく書く（書き換えでは通知が飛ばないため）。
- 段階2と「Ready for review の後」の手順1で Issue と PR のコメントを読むため、ここに残したものは次のセッションに引き継がれる。

## 使い方

```
/resolve-issue <issue番号>
```

## 段階の判定

1. `gh issue view <番号> --comments` でIssueを読む。
2. 対応するPRを探す（`gh pr list --head <ブランチ名>`、見つからなければ `gh pr list --search "#<番号>"`）。
3. 状態で分岐する。
   - PRが無い → 段階1
   - Draft → 段階2。呼び直されたこと自体を、設計が承認された合図とみなす
   - Ready for review → 「Ready for review の後: 指摘に対応する」に従う

段階1を終えたのと同じセッションで呼ばれた場合は、段階2に進まず、セッションを作り直してから呼び直すよう伝える。

## 段階1: 設計する

1. ブランチを作る。`AGENTS.md` に指示（worktree を使わない、など）があれば従う。名前は `fix/issue-<番号>` または `feature/issue-<番号>`。
2. Issue本文とコメントを読み、受入条件を設計の入力として確かめる。設計できないほどの要件の抜け（期待結果が `？` のままの行、決まっていない境界値や異常系、条件どうしの矛盾、受入条件そのものが無いなど）を見つけたら、推測で埋めず、受入条件も書き換えずに、手順4で人に問う。
3. Issue の要件をもとに、`design-docs` で設計ドキュメントに落とし込む。Issue のコメントも拾って反映する。設計ドキュメントが無いリポジトリでは作らない（「書き残す先」）。
   - `requirements.md` は設計というより要件定義だが、この段階で更新する。Issue の要件をもとに、システム全体の要件として組み直す。Issue 単位の要件定義（`create-issue`）と、システム全体への組み込み（このスキル）という開発プロセスの切れ目を優先するため。
   - 仕様・設計のファイルには、Issue の要件を満たすための仕様と、設計の途中で生じた判断とその理由、制約などを書く。
4. コミットして push し、`create-pullrequest` で **Draft PR** を作る。設計ドキュメントの差分が無い場合は `git commit --allow-empty` で空のコミットを作る。本文の冒頭に、確認してほしいこと（設計ドキュメントの差分、手順2で見つけた要件の抜けと `？` の行）を並べる。
5. 段階2の実装者が知る必要のあること（調べて分かった制約、選ばなかった案とその理由など）の要点を PR本文に書く。設計の途中で生じた情報のうち、設計ドキュメントに残さなかったものは PRコメントに書く。
6. 人に設計の確認を頼んで止まる。要件の抜けがあれば、Issue 側で答えてもらうよう頼む（要件を補うのは要件定義の作業のため）。確認が済んだら、セッションを作り直して同じIssueで呼び直すよう伝える。

## 段階2: 実装する

1. Issue本文、PR本文、Issue と PR のコメントを読み、段階1で決めたことと人のレビューを把握する。`？` の行や要件の抜けが残っていて答えも無ければ、実装に入らず人に問う。答えが Issue のコメントにあって本文に反映されていなければ、`create-issue` の「起票後に要件を補う」に従って Issue 本文に反映する。
2. 実装前のテストの成否を記録する（後で「元々失敗していたテスト」と「新たに壊したテスト」を区別するため）。
3. `test-as-tdd` に従い、テストとプロダクトコードを交互に書く。
   - テストの種類（単体、UI、E2E）と書き方は、プロジェクトの既存のテストに合わせる。受入条件のために新しい規約を作らない。
   - 受入条件の表の行は、テストのデータとしてそのまま写す。テスト名か説明に条件番号を含め（例: `条件2: JSONにない馬番は既存のまま残す`）、人が Issue の表と見比べられるようにする。
4. **受入条件を自分の判断で変えない。** 実装中に受入条件が間違っていると判断したら、理由と修正案を `create-issue` の「起票後に要件を補う」に従って Issue コメントで示し、人の判断を待つ。受入条件の変更は要件定義の作業で、人が決める。判断が出たら、同じ手順で Issue 本文に反映する。
5. 設計ドキュメントを見直す。食い違いの有無にかかわらず、Issue のコメントを拾い、設計ドキュメントに残すべきもの（段階1の後に書かれたものを含む）を反映する。実装後に設計ドキュメントとコードが食い違ったら、コードを正としてドキュメントを直し、その旨をPR本文に書く。
6. 実装の途中で分かった考え・暗黙知・調査結果は、まず設計ドキュメントに残すべきかを考える。残すべきもの（判断の理由、制約など）は手順5と同じく設計ドキュメントに反映し、残すべきでないもの（デバッグ中の CI の結果など）は PRコメントに書く。
7. `test-code` で品質ゲートを通す。手順2で記録した元々の失敗は無視してよいが、新たに失敗するようになったテストは直す。
8. コミットして push し、PR本文を更新する（動作確認、受入条件ごとの対応するテスト）。Draft の間は、コミットのたびに push してよい。
9. Ready にする前に、push するものをすべて片付ける。品質ゲート、PR本文、自動チェック（セキュリティレビューなど）の指摘への対応まで終えて push してから、`gh pr ready <PR番号>` で Ready for review にする。Ready の後の push は CI のやり直しになるため（次節）。マージはユーザーの判断で、このスキルの範囲はここまで。

## Ready for review の後: 指摘に対応する

Ready の PR への push は、**ひとまとまりの対応ごとに1回** にする。push するたびに実行中の CI が取り消されて最初からやり直しになり、途中の状態でレビュアーに通知も飛ぶため。CI の所要時間など、リポジトリに固有の事情は各リポジトリの `AGENTS.md` に従う。

1. Issue本文と Issue のコメント、PR のレビューとコメントを読み、そのとき来ている指摘をすべて把握する。Issue 側は、受入条件と、段階1の後に書かれた制約や判断を把握するために読む。自動チェック（セキュリティレビューなど）の指摘も、人のレビューの指摘と同じに扱う。
2. 指摘をすべて直す。直し方は段階2の手順3〜5に従う。コミットは指摘ごとに分けてよいが、1件直すたびに push しない。
3. 指摘を直す途中で、または指摘とは関係なく、残したほうがいい考え・暗黙知・調査結果（直し方を選んだ理由、見つけた制約など）が生じたら、まず設計ドキュメントに残すべきかを考える。残すべきものは、ここで `design-docs` で設計ドキュメントに反映する（手順5の push に含めるため、push の後に直さない）。残すべきでないものは、手順6で PR に新規コメントとして書く。
4. `test-code` でローカルの品質ゲートを通す。
5. 1回 push し、`create-pullrequest` で PR本文の動作確認を更新する。
6. コードに付いた指摘ごとに、その指摘へのリプライとして対応を書く（どう直したか、直さなかった・別の直し方を採った理由など）。`gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -f body=...` でそのスレッドに返す。リプライへのリプライは API が受け付けないため、`<コメントID>` にはスレッドの最初のコメントの ID を使う。コードに付いていないコメントには返信しない（PR 上で議論はしないため）。手順3で PR コメントに回したものは、ここで新規コメントとして書く。push の後に書くのは、コメントが push 済みのコミットを指せるようにするため。

まれに次の状況になる。

- **直している途中で新しい指摘が届いた**: 新しい指摘も含めてすべて直し、品質ゲートを通してから1回 push する。途中で push しても、次の push で CI が取り消されるため。
- **指摘の一部が人の判断待ち**: 直した分を先に1回 push し、判断待ちの指摘は PRコメントで問う。判断が出て直したら、もう一度 push する。判断を待つと、直した分の検証が止まるため。

## コミット

作業ブランチ上では、各段階の手順に従い、コミット・push・PR作成・PR本文更新・PR へのコメント・`create-issue` に従った Issue への反映・Ready for review への変更まで、操作ごとの許可をユーザーに求めずに進める。設計の確認、受入条件の変更の判断と、段階間のセッション切り替えは、各段階に記載したとおりに行う。マージはユーザーの判断とする。

コミットメッセージに Issue 番号を含める（`Refs #<番号>`）。PR本文に `Closes #<番号>` を書く。

## 出力形式

各段階の終わりに、PRのURLと人に見てほしいことを示す。

- 段階1: 確認してほしい設計ドキュメントの差分、見つけた要件の抜けと `？` の行（Issue 側で答えてほしいこと）、そして「確認後にセッションを作り直して呼び直す」こと
- 段階2: UATで参考にする受入条件

## 他のスキルとの関係

| スキル | 使う場面 |
| :--- | :--- |
| `create-issue` | 要件の抜けへの答えや受入条件の変更を Issue に反映するとき（「起票後に要件を補う」） |
| `create-pullrequest` | 段階1の Draft PR 作成、段階2と Ready の後の本文更新 |
| `design-docs` | 段階1の設計ドキュメント更新、段階2の食い違いの修正と実装中に分かったことの反映、Ready の後に分かったことの反映 |
| `test-as-tdd` | 段階2のテストと実装 |
| `test-code` | 段階2と Ready の後の品質ゲート |

## サンプル対話

**User:** /resolve-issue 44

**Agent:** Issue #44 を確認しました。PRはまだ無いので、段階1（設計）から始めます。受入条件の2番目の表で、「既存のレースにあってJSONに無い馬番をどう扱うか」が `？` のままでした。推測で埋めず、受入条件も変えずに、要件の抜けとして PR本文の冒頭に並べました。設計ドキュメントを更新し、Draft PR を作成しました。URL: ... 設計ドキュメントの差分をご確認のうえ、`？` の行には Issue で答えてください。確認が済んだら、セッションを作り直して `/resolve-issue 44` を呼び直してください。

**User:** （Issueに「JSONに無い馬番は残す」とコメントし、`/clear` してから）/resolve-issue 44

**Agent:** Draft PR があるので段階2として進めます。Issueのコメントから、`？` の行は「既存のまま残す」と読み取り、`create-issue` の手順で Issue本文の表に反映しました。TDD でテストと実装を進め、品質ゲートを通したうえで Ready for review にしました。URL: ... UATでは Issue の受入条件を参考にご確認ください。
