# リファクタリング基準

`SKILL.md` と付随ファイルを整理するときの詳細な判断基準と書き換え例です。

## 1. パッチの4分類と対処方針

| 分類 | 見分け方 | 対処方針 |
| :--- | :--- | :--- |
| **重複している指示** | 同じルールが概要・手順・注意点に少しずつ違う言い回しで繰り返し登場する | 最も効く1箇所（原則または該当ステップ）に統合し、残りを削る |
| **互いに矛盾している指示** | 「常に〜する」と「〜のときはしない」など、後付けのパッチ同士が食い違っている | 勝手に片方を消さない。どちらを優先するかユーザーに確認して1つに統一する |
| **特定の一件のために足された例外** | 特定のファイル名・ツール名・1回限りの事故をそのまま「〜するな」で書いている | 背後にある原則を引き出し、例外は代表例を1つ添える形に畳む |
| **今のモデルなら言われなくてもできること** | 「丁寧に確認する」「わかりやすく説明する」「エラーを無視しない」などの一般論や、旧モデルの癖を抑えるためだけの指示 | 削る。迷ったら「この行を消したら現行モデルが本当に間違えるか？」で判定する |

### 提示する分類表のフォーマット例（ステップ2）

ステップ2では、ユーザーが一目で判断できるよう次の形式で提示します。

```markdown
| 対象箇所 | 分類 | 整理方針 |
| :--- | :--- | :--- |
| 概要・手順3の「確認なしに上書きしない」 | 重複 | 大原則の1箇所に統合 |
| 「出力は短く」vs「全項目を詳細に書く」 | 矛盾 | どちらを優先するか確認したい |
| 「foo.json は編集するな」「bar.lock は触るな」 | 特定の一件の例外 | 「生成ファイルを手動編集しない」の原則にまとめ、例を1つ添える |
| 「丁寧にわかりやすく回答すること」 | 言われなくてもできること | 削除 |
| 言語別チェックリスト（120行） | 構造分離候補 | `references/` へ移動し条件付きリンクに変更 |
```

## 2. 理由つきで一つにまとめる（書き換え例）

### 「〜するな」の羅列 → 原則＋1行の理由

禁止を列挙すると抜け漏れが増え、さらにパッチが積み上がる原因になります。理由を1行添えた原則にすると、列挙していない似た場面にも効きます。

**Before:**
```markdown
- テストファイルを勝手に消さないこと
- カバレッジの閾値を下げないこと
- 失敗したテストを skip にしないこと
- リンターのルールを無効化コメントで黙らせないこと
```

**After:**
```markdown
- **検査を緩めて合格させない**: 問題の見落としを防ぐため、テストの削除・スキップ、閾値の引き下げ、リンター無効化で通さず原因を直す。
```

### 特定の一件の例外の積み上げ → 原則＋代表例1つ

個別の例外を毎回足すと際限なく膨らみます。共通する原則を述べ、代表的な例を1つだけ添えます。

**Before:**
```markdown
- `package-lock.json` を手で書き換えないこと
- `yarn.lock` を手で書き換えないこと
- `go.sum` を手で書き換えないこと
- `generated/schema.ts` を手で書き換えないこと
```

**After:**
```markdown
- **自動生成ファイルを手動編集しない**: 次の生成で上書きされ差分が壊れるため、元の定義を編集してツールで再生成する（例: ロックファイルやスキーマ生成物）。
```

## 3. 構造を分ける判断基準

| 配置先 | 置くもの | 判断の目安 |
| :--- | :--- | :--- |
| **`SKILL.md`** | 目的・大原則・基本の流れ・各ファイルへの導線 | スキル発火時に毎回読まれる。短く保ち、「いつ何を読むか」の地図にする |
| **`references/`** | 細かいルール、判断表、言語・ケース別手順、Before/After 例 | 特定の条件や迷ったときだけ必要な知識。`SKILL.md` から条件付きでリンクする |
| **`scripts/`** | 検証・整形・抽出・集計・リンクチェックなどの決まりきった処理 | 文章で手順を書くと長く、実行のたびにブレやすい機械的処理 |
| **`assets/`** | 出力テンプレート、スキーマ、定型ファイル | そのままコピー・参照して使う静的素材 |

### 条件付きリンクの書き方

`references/` に分けたファイルは、`SKILL.md` で「いつ読むか」を明示してリンクします。毎回全部読ませる書き方にすると分離した意味が薄れます。

- 良い例: `TypeScript プロジェクトの場合は [TypeScript 手順](references/typescript.md) を読む。`
- 避けたい例: `詳細は references/ 以下のファイルをすべて読むこと。`

## 4. 削ってはいけないもの

短くすることが目的化すると、スキルが効かなくなります。次は必ず残します。

- **非自明な制約・落とし穴**: 一般知識やコードから推測できない、そのプロジェクト・ドメイン固有のルール
- **ユーザーが明示した非交渉事項**: 過去に何度も問題になり、明示的に固定した方針
- **`description` の発火トリガー**: ユーザーが実際に言いそうな英語・日本語の表現（発火は `description` だけで判定される）
- **手順の順序制約**: 順番を入れ替えると壊れる工程（「先に分類だけ見せてから直す」など）
