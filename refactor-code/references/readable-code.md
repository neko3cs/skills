# 読みやすさの共通原則

全言語に共通する、読みやすさの判断基準です。Dustin Boswell / Trevor Foucher『リーダブルコード』（オライリー・ジャパン、2012年）の考え方を、このスキル向けに要約・再構成しています。本文の引用ではありません。

言語ごとの具体的な書き換えは [言語別パターン](language-patterns.md) にあります。両者が食い違う場合は、プロジェクトの既存規約 → 言語別パターン → この原則の順に優先してください。

## 判断の物差し

**「他の人がこのコードを理解するまでにかかる時間」を最小にする。** 行数の少なさより、この時間を優先します。短くしても読む時間が増えるなら、それは改善ではありません。「他の人」には、数か月後の自分も含みます。

## 1. 表面上の改善

### 名前に情報を込める

- `get` / `process` / `handle` / `data` / `tmp` / `retval` のような汎用的な語は、何を・どうするのかが分かる具体的な語に替える。`tmp` が許されるのは、数行で役目を終える本当に一時的な値だけ。
- 単位や状態など、取り違えると事故になる情報は名前に入れる（`delayMs`、`unsafeHtml`、`plaintextPassword`）。
- 名前の長さはスコープに比例させる。数行のループ変数は短くてよく、広く使われる名前ほど具体的にする。
- 誤解されない名前にする。範囲は `min` / `max`（含む）、`first` / `last`（含む）、`begin` / `end`（終端を含まない）を使い分ける。bool は `is` / `has` / `can` / `should` で始め、否定形（`disableX`）を避ける。
- 利用者の期待に合わせる。`get` や `size` のような名前は「軽い処理」と期待されるので、重い処理には `compute` / `fetch` などを使う。

### 見た目を整える

- 似た処理は同じ形に揃え、違いが目立つようにする。
- 関係のある行をまとめ、まとまりの間に空行を入れる。
- 宣言や引数の並び順に一貫性を持たせる（重要度順、定義順など）。どれか1つに決めて全体で守る。
- 整形はフォーマッタに任せ、手で揃えた独自の整形は持ち込まない。

### コメントは「コードから読み取れないこと」だけを書く

- 消すもの: コードを読めば分かることの言い換え。名前が悪いのを補うコメント（名前の方を直す）。
- 書くもの:
  - 設計の意図・なぜこの方法を選んだか・却下した代替案
  - 既知の欠陥や制約（`TODO` / `FIXME` などプロジェクトの記法で）
  - 定数の値の根拠
  - 読み手がつまずきそうな箇所、驚きそうな振る舞いの先回り
  - ファイルや大きな処理の全体像（どの順に何が起きるか）
- 曖昧な代名詞や抽象的な言い回しを避け、入出力の具体例で示せるなら例を書く。

## 2. ループとロジックの単純化

### 制御フローを読みやすくする

- 条件式は、変化する値を左に、比較対象（定数など）を右に置く。
- `if / else` は、肯定形・単純な方・目立つ方を先に書く。
- 三項演算子は、`if / else` より明らかに読みやすいときだけ使う。
- 早期 return・ガード節でネストを浅くする。ネストが深くなったら、まず早期 return で外せないか考える。
- 実行の流れを追いにくくする仕組み（スレッド、コールバック、例外による大域脱出など）は、必要な箇所に絞る。

### 巨大な式を分割する

- 長い式や長い条件は、意味のある名前の変数に分ける（**説明変数**・**要約変数**）。
- ド・モルガンの法則で否定を外側にくくり出し、読みやすい形にする。
- 短絡評価を使った「賢い」1行は、分かりやすい複数行に戻す。

### 変数を減らし、寿命を短くする

- 読みやすさに貢献しない中間変数は消す。**ただし、式に名前を付けて意図を伝える説明変数・要約変数は残す。** 消すか残すかは「名前が新しい情報を足しているか」で判断する。
- 変数のスコープはできるだけ狭くする。クラスのメンバーやグローバル変数は、本当に必要なものだけにする。
- 一度だけ代入する変数を好む（`const` / `let` / `readonly` / `final` など）。値が何度も変わる変数ほど、追跡が難しくなる。
- 制御用のフラグ変数は、早期 return や `break` で置き換えられないか考える。

## 3. コードの再構成

### 無関係の下位問題を抽出する

- 関数の本来の目的と直接関係しない処理（文字列整形、汎用的な計算、外部APIの使いにくさの吸収など）は、別の関数に切り出す。
- 抽出の基準は「その処理を単独で説明できるか」。一度しか使わなくても、本来の目的が読みやすくなるなら切り出す。逆に、切り出しても本来の目的が読みやすくならない細切れの関数は作らない。
- 使いにくいインターフェースは、薄いラッパーで使いやすい形にしてから使う。

### 一度に1つのことをする

- 1つの関数が複数の仕事を混ぜて行っているなら、仕事ごとに分けて並べる（または別関数にする）。
- 「このコードは何をしているか」を列挙し、仕事ごとに領域を分けてから並べ替える。

### 考えを言葉にしてからコードにする

- 処理を簡単な言葉で説明してみて、その説明に近い形にコードを書き直す。説明に出てこない処理は、不要か別の場所に属するもの。

### 短いコードを書く

- 要件のうち、本当に必要なものだけを実装する。使われない機能・汎用化・設定項目は削る。
- 標準ライブラリや既存の関数で済むことは、自前で書かない。
- 使われていないコードは消す。必要になればバージョン管理から戻せる。

## 4. テストの読みやすさ

- テストは、テストする内容以外の詳細を隠し、何を確かめたいのかが一目で分かる形にする。準備の手順が長ければヘルパーに切り出す。
- 失敗したときのメッセージで原因が分かるようにする（期待値と実際の値が見えるアサーションを使う）。
- 入力は、問題を確かめられる中で最も単純で、意図が伝わる値を選ぶ。
- 1つのテストで1つの振る舞いを確かめ、テスト名でその振る舞いを表す（命名は `test-as-tdd` の規則に従う）。
- テストしやすいコードは、たいてい読みやすいコードでもある。テストが書きにくい箇所は、本体の設計を見直すきっかけにする。
