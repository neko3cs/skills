# implement-design Skill

## 概要

設計文書に書かれたことを、Issue 1つにつき1つの実装PRで実装します。何を作るかは設計文書から読み、Issue は作業範囲と `Closes #<番号>` の紐付けに使います。

- **正本は設計文書です。** 受け入れ基準は `requirements.md`、入力から結果が決まる規則は `specification.md` の業務ルールにあります。テストはその写しです。
- **設計はこのスキルの範囲外です。** 設計文書が足りなければ、推測で埋めず、自分で設計もせずに止まります。設計は設計PRとしてマージ済みであることが前提です。
- 正しい動作がすでに設計文書に書かれているバグ修正などは、設計PRを経ずにこのスキルから始められます。

## 使い方

```
/implement-design <issue番号>
```

## 最初に確かめる

1. `gh issue view <番号> --comments` で Issue を読む。
2. 同じ Issue の実装PRを探す（`gh pr list --head <ブランチ名>`、見つからなければ `gh pr list --search "#<番号>"`）。Ready for review の実装PRがあれば「Ready for review の後: 指摘に対応する」に進む。
3. 依頼されたPRの差分が設計文書だけなら、設計PRのレビュー対応なので、設計文書の更新で直すよう伝えて止まる（このスキルは設計しない）。
4. 既定ブランチを最新にし、作業範囲を決める。
   - `grep -rn "未実装 #<番号>"` で印の付いた箇所を探す。
   - `gh pr list --state merged --search "#<番号>"` で設計PRを探し、あればその差分も作業範囲に含める。
   - どちらも無ければ（バグ修正など）、Issue の内容が書かれている設計文書の箇所を作業範囲にする。
5. 次のどれかに当たれば、不足を具体的に伝えて止まる。実装は始めない。
   - 設計文書が無い。
   - Issue の内容が設計文書に書かれていない。設計PRが未マージで見つかったら、そう伝える。
   - 作業範囲に `？`（業務ルールの表で期待結果が決まっていない行）や `TBD` が残っている。

## 書き残す先

会話の中だけにあった考えは、次に読む人には届きません。次のセッションや後から読む人に必要な考え・暗黙知・調査結果は、生じたときに書き残します。

| 残す先 | 残すもの |
| :--- | :--- |
| 設計文書 | 判断の理由、仕様、制約など、設計文書に残すべき情報。`design-docs` で書く |
| PR本文 | PRの概要、レビューしてほしい設計判断、動作確認 |
| PR コメント | 設計文書に残すべきでない情報（デバッグ中の CI の結果など） |

- Issue は読むだけで、書かない。
- 残すのは、次に読む人が会話を持たずに困るものに限る。作業の実況や、コードやコミットを読めば分かることは書かない。
- 同じ話題の PR コメント（方針の決定など）の内容が変わったら、新しいコメントを足さず、既存のコメントを書き換える（`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...`）。PR本文も最新に保つ。古い決定が並ぶと、次に読む人が迷うため。ただし、コードへの指摘へのリプライと、人に判断を問うコメントは新しく書く（書き換えでは通知が飛ばないため）。

## 実装する

1. 既定ブランチからブランチを作る。`AGENTS.md` に指示（worktree を使わない、など）があれば従う。名前は `fix/issue-<番号>` または `feature/issue-<番号>`。
2. 実装前のテストの成否を記録する（後で「元々失敗していたテスト」と「新たに壊したテスト」を区別するため）。
3. `test-as-tdd` に従い、テストとプロダクトコードを交互に書く。
   - テストの種類（単体、UI、E2E）と書き方は、プロジェクトの既存のテストに合わせる。
   - 業務ルールの表の行は、テストのデータとしてそのまま写す。テスト名か説明に、設計文書の該当箇所が分かる言葉を含め、人が表と見比べられるようにする。
4. **設計文書の受け入れ基準や業務ルールを自分の判断で変えない。** 間違っていると判断したら、理由と修正案を PR コメントで問い、人の判断を待つ。判断が出たら、同じ実装PRの中で `design-docs` を使って直す。
5. `design-docs` で設計文書を更新する。
   - 実装した箇所の `未実装 #<番号>` の印を外す。実装していない箇所の印は残す。
   - 実装後に設計文書とコードが食い違ったら、コードを正として設計文書を直し、その旨を PR本文に書く。
   - 実装の途中で分かった考え・暗黙知・調査結果のうち、設計文書に残すべきもの（判断の理由、制約など）を反映する。残すべきでないものは PR コメントに書く。
6. `test-code` で品質ゲートを通す。手順2で記録した元々の失敗は無視してよいが、新たに失敗するようになったテストは直す。
7. コミットして push し、`create-pullrequest` で実装PRを作る（または本文を更新する）。本文には `Closes #<番号>`、動作確認、受け入れ基準ごとの対応するテストを書く。Ready にする前なら Draft で作り、コミットのたびに push してよい。
8. Ready にする前に、push するものをすべて片付ける。品質ゲート、PR本文、自動チェック（セキュリティレビューなど）の指摘への対応まで終えて push してから、`gh pr ready <PR番号>` で Ready for review にする。Ready の後の push は CI のやり直しになるため（次節）。マージはユーザーの判断で、このスキルの範囲はここまで。

## Ready for review の後: 指摘に対応する

Ready の PR への push は、**ひとまとまりの対応ごとに1回** にする。push するたびに実行中の CI が取り消されて最初からやり直しになり、途中の状態でレビュアーに通知も飛ぶため。CI の所要時間など、リポジトリに固有の事情は各リポジトリの `AGENTS.md` に従う。

1. 設計文書の作業範囲と、PR のレビューとコメントを読み、そのとき来ている指摘をすべて把握する。自動チェック（セキュリティレビューなど）の指摘も、人のレビューの指摘と同じに扱う。
2. 指摘をすべて直す。直し方は「実装する」の手順3〜5に従う。コミットは指摘ごとに分けてよいが、1件直すたびに push しない。
3. 残したほうがいい考え・暗黙知・調査結果（直し方を選んだ理由、見つけた制約など）が生じたら、設計文書に残すべきものは、ここで `design-docs` で反映する（手順5の push に含めるため）。残すべきでないものは、手順6で PR に新規コメントとして書く。
4. `test-code` でローカルの品質ゲートを通す。
5. 1回 push し、`create-pullrequest` で PR本文の動作確認を更新する。
6. コードに付いた指摘ごとに、その指摘へのリプライとして対応を書く（どう直したか、直さなかった・別の直し方を採った理由など）。`gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -f body=...` でそのスレッドに返す。リプライへのリプライは API が受け付けないため、`<コメントID>` にはスレッドの最初のコメントの ID を使う。コードに付いていないコメントには返信しない（PR 上で議論はしないため）。手順3で PR コメントに回したものは、ここで新規コメントとして書く。push の後に書くのは、コメントが push 済みのコミットを指せるようにするため。

まれに次の状況になる。

- **直している途中で新しい指摘が届いた**: 新しい指摘も含めてすべて直し、品質ゲートを通してから1回 push する。
- **指摘の一部が人の判断待ち**: 直した分を先に1回 push し、判断待ちの指摘は PRコメントで問う。判断が出て直したら、もう一度 push する。

## コミット

作業ブランチ上では、コミット・push・PR作成・PR本文更新・PR へのコメント・Ready for review への変更まで、操作ごとの許可をユーザーに求めずに進める。マージはユーザーの判断とする。

コミットメッセージに Issue 番号を含める（`Refs #<番号>`）。PR本文に `Closes #<番号>` を書く。

## 出力形式

終わりに、PRのURLと、UATで参考にする受け入れ基準（設計文書の該当箇所）を示す。止まった場合は、足りないもの（設計文書のどこに何が無いか、どの `？` / `TBD` が残っているか）を示す。

## 他のスキルとの関係

| スキル | 使う場面 |
| :--- | :--- |
| `test-as-tdd` | テストと実装 |
| `test-code` | 品質ゲート |
| `design-docs` | 印を外す、食い違いの修正、実装中に分かったことの反映、人が決めた設計文書の修正 |
| `create-pullrequest` | 実装PRの作成と本文の更新 |

## サンプル対話

**User:** /implement-design 44

**User:** （設計PRで `？` を「既存のまま残す」に直してマージしてから）/implement-design 44

**Agent:** 作業範囲は業務ルール「馬番の取り込み」です。TDD でテストと実装を進め、印を外し、品質ゲートを通したうえで Ready for review にしました。URL: ... UATでは `specification.md` の業務ルール「馬番の取り込み」を参考にご確認ください。
