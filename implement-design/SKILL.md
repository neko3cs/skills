# implement-design Skill

## 概要

設計文書に書かれたことを、Issue 1つにつき1つの実装PRで実装します。何を作るかは設計文書から読み、Issue は作業範囲と `Closes #<番号>` の紐付けに使います。

- **正本は設計文書です。** 受け入れ基準は `requirements.md`、入力から結果が決まる規則は `specification.md` の業務ルールにあります。テストはその写しです。
- **通常は設計完了・マージ後に実装します。** 実装依頼の範囲に不足・未決事項が見つかった場合は、`design-docs` で仮案と理由を明示し、同じ実装PRで実装・検証してPRコメントで質問します。設計不足・未マージ時の仮実装は例外として認めますが、設計前の実装を通常の運用にはしません。仮案を合意済みと扱わず、PR作成前に会話で判断待ちにしません。
- 正しい動作がすでに設計文書に書かれているバグ修正などは、設計PRを経ずにこのスキルから始められます。

## 使い方

```
/implement-design <issue番号>
```

## 最初に確かめる

1. `gh issue view <番号> --comments` で Issue を読む。
2. 同じ Issue の実装PRを探す（`gh pr list --head <ブランチ名>`、見つからなければ `gh pr list --search "#<番号>"`）。差分が設計文書だけのPRは設計PRなので、実装PRとして扱わない。
   - Ready for review の実装PRがある → 「Ready for review の後: 指摘に対応する」に進む。
   - Draft の実装PRがある → そのブランチに切り替え、手順5の確認をしてから「実装する」の続きを進める（ブランチもPRも作り直さない）。作業範囲と残作業は Issue、PR本文、差分から読み、設計文書の該当箇所と照合する。
3. 依頼されたPRの差分が設計文書だけなら、`design-docs` でそのPRのレビュー対応を行う。実装PRは新しく作らない。
4. 既定ブランチを最新にし、作業範囲を決める。
   - Issue の本文・コメントから対象の機能と変更要求を読み、`gh pr list --state merged --search "#<番号>"` で関連する設計PRを探す。検索結果は本文と差分を読み、対象Issueに関係するものか確認する。
   - 設計PRがあれば、その本文・レビュー・差分から変更された仕様を把握し、現在の設計文書の該当箇所と照合して作業範囲を決める。無関係な変更は含めない。
   - 設計PRが無ければ（バグ修正など）、Issue の変更要求を設計文書の該当箇所と照合して作業範囲を決める。設計文書内のIssue番号や実装状況のマーカーには依存しない。
5. 次のどれかに当たれば、`design-docs` で不足箇所に具体的な仮案と理由を記載し、その仮案で実装・検証を進める。仮案と影響は PR本文に要約し、「判断待ちがある場合」に従って別途PRコメントで質問する。
   - 設計文書が無い。
   - Issue の内容が設計文書に書かれていない。設計PRが未マージで見つかったら、そう伝える。
   - 作業範囲に `TBD`（業務ルールの表で期待結果が決まっていない行など）が残っている。

## 書き残す先

会話の中だけにあった考えは、次に読む人には届きません。次のセッションや後から読む人に必要な考え・暗黙知・調査結果は、生じたときに書き残します。

| 残す先 | 残すもの |
| :--- | :--- |
| 設計文書 | 判断の理由、仕様、制約など、設計文書に残すべき情報。`design-docs` で書く |
| PR本文 | PRの概要、仮案と確認状況の要約、動作確認 |
| PR コメント | 仮案への具体的な質問、設計文書に残すべきでない情報（デバッグ中の CI の結果など） |

- Issue は読むだけで、書かない。
- 残すのは、次に読む人が会話を持たずに困るものに限る。作業の実況や、コードやコミットを読めば分かることは書かない。
- 同じ話題の PR コメント（方針の決定など）の内容が変わったら、新しいコメントを足さず、既存のコメントを書き換える（`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<コメントID> -f body=...`）。PR本文も最新に保つ。古い決定が並ぶと、次に読む人が迷うため。ただし、コードへの指摘へのリプライと、人に判断を問うコメントは新しく書く（書き換えでは通知が飛ばないため）。

## 実装する

1. 既定ブランチからブランチを作る。`AGENTS.md` に指示（worktree を使わない、など）があれば従う。名前は `fix/issue-<番号>` または `feature/issue-<番号>`。
2. 実装前のテストの成否を記録する（後で「元々失敗していたテスト」と「新たに壊したテスト」を区別するため）。
3. `test-as-tdd` に従い、テストとプロダクトコードを交互に書く。
   - テストの種類（単体、UI、E2E）と書き方は、プロジェクトの既存のテストに合わせる。
   - 業務ルールの表の行は、テストのデータとしてそのまま写す。テスト名か説明に、設計文書の該当箇所が分かる言葉を含め、人が表と見比べられるようにする。
4. **合意済みの受け入れ基準や業務ルールと、未承認の仮案を区別する。** 不足・未決事項には `design-docs` で仮案を書いてから、その期待動作を実装・検証する。既存仕様が間違っていると判断した場合は、元の決定と理由を保持し、修正案を未承認の提案として同じPRに示す。仮案への質問は「判断待ちがある場合」に従い、回答後に文書・実装・テストを揃える。
5. 設計文書とコードを突き合わせる。
   - 作業範囲の中で食い違いがあれば、文書に記載した仕様・仮案を正としてコードを直す（利用者が確認するのは文書で、コードはあまり読まないため）。文書をコードに合わせて書き換えない。文書のほうが間違っていると判断したら、手順4に従って修正案を示す。
   - 作業範囲の外で見つけた食い違いは、直さずに PR コメントで知らせる（別の不具合として扱うため）。
6. `design-docs` で設計文書を更新する。
   - 設計文書は Issue・PR・コードから独立して仕様と仮案を理解できる状態に保ち、未実装でこれから実装が必要であることを示すメモは残さない。実装済み・保留の範囲と仮案の確認状況は PR本文で管理する。
   - 実装の途中で分かった考え・暗黙知・調査結果のうち、設計文書に残すべきもの（判断の理由、制約など）を反映する。残すべきでないものは PR コメントに書く。
7. `test-code` で品質ゲートを通す。手順2で記録した元々の失敗は無視してよいが、新たに失敗するようになったテストは直す。
8. コミットして push し、`create-pullrequest` で実装PRを作る（または本文を更新する）。本文には動作確認、受け入れ基準ごとの対応するテストを書く。Issue の紐付けは「コミット」節に従い `Closes #<番号>` とする。Ready にする前なら Draft で作り、コミットのたびに push してよい。
9. Ready にする前に、push するものをすべて片付ける。品質ゲート、PR本文、自動チェック（セキュリティレビューなど）の指摘への対応まで終えて push してから、`gh pr ready <PR番号>` で Ready for review にする。Ready の後の push は CI のやり直しになるため（次節）。マージはユーザーの判断で、このスキルの範囲はここまで。

### 判断待ちがある場合

ユーザーへの確認は、仮案による設計・実装・検証を示したうえでPRコメントで行います。判断待ちを理由に、コミット・push・PR作成の前で作業を終えません。

- 会話・既存仕様・コードから妥当な仮案を選び、`design-docs` で `仮定（未承認）` と理由を記載し、同じ実装PRでTDDによる実装と品質ゲートを進める。
- 仮案、実装した範囲、検証結果、未完了項目を PR本文に記載して Draft PRを作成・更新する。回答を反映して設計・実装を整え、必要な検証を終えるまで Draft を維持する。すでに Ready なら Draft に戻す。仮案のテストが成功しても、仕様が承認されたとは報告しない。
- `create-pullrequest` の質問コメントの手順に従い、対象の節・実装箇所、採用した仮案と理由、具体的な入力と結果、主要な代替案と影響を示して質問する。回答で案を変える場合は、同じPRで設計文書・コード・テストを修正し、再検証する。採用が確認されたら仮定の表示とPR本文を更新し、残りの判断待ちと品質ゲートを確認して Ready にする。
- 資格情報や実測結果などの不足は仮定で補わない。仮案を実装・検証できない箇所は、制約・進めた範囲・必要な情報を具体的に示す。PR URLと質問コメントを提示し、レビューできる状態で終了する。

## Ready for review の後: 指摘に対応する

Ready の PR への push は、**ひとまとまりの対応ごとに1回** にする。push するたびに実行中の CI が取り消されて最初からやり直しになり、途中の状態でレビュアーに通知も飛ぶため。CI の所要時間など、リポジトリに固有の事情は各リポジトリの `AGENTS.md` に従う。

1. Issue、PR の差分と PR本文（受け入れ基準ごとの対応するテスト）を設計文書と照合して作業範囲を読み、PR のレビューとコメントを読んで、そのとき来ている指摘をすべて把握する。自動チェック（セキュリティレビューなど）の指摘も、人のレビューの指摘と同じに扱う。
2. 指摘をすべて直す。直し方は「実装する」の手順3〜6に従う。コミットは指摘ごとに分けてよいが、1件直すたびに push しない。
3. 残したほうがいい考え・暗黙知・調査結果（直し方を選んだ理由、見つけた制約など）が生じたら、設計文書に残すべきものは、ここで `design-docs` で反映する（手順5の push に含めるため）。残すべきでないものは、手順6で PR に新規コメントとして書く。
4. `test-code` でローカルの品質ゲートを通す。
5. 1回 push し、`create-pullrequest` で PR本文の動作確認を更新する。
6. コードに付いた指摘ごとに、その指摘へのリプライとして対応を書く（どう直したか、直さなかった・別の直し方を採った理由など）。`gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -f body=...` でそのスレッドに返す。リプライへのリプライは API が受け付けないため、`<コメントID>` にはスレッドの最初のコメントの ID を使う。コードに付いていないコメントへの定型返信は不要だが、仮案への回答は読み取り、文書・実装・テストとPR本文に反映する。新たな判断が必要なら別途新規コメントで質問する。手順3で PR コメントに回したものは、ここで新規コメントとして書く。push の後に書くのは、コメントが push 済みのコミットを指せるようにするため。

まれに次の状況になる。

- **直している途中で新しい指摘が届いた**: 新しい指摘も含めてすべて直し、品質ゲートを通してから1回 push する。
- **指摘の一部が人の判断待ち**: 直した分を先に1回 push し、「判断待ちがある場合」に従って Draft に戻し、確認事項を PR本文と該当のレビュースレッドに残す。判断が出て直したら、もう一度 push する。

## コミット

作業ブランチ上では、コミット・push・PR作成・PR本文更新・PR へのコメント・Ready for review への変更まで、操作ごとの許可をユーザーに求めずに進める。マージはユーザーの判断とする。

コミットメッセージに Issue 番号を含める（`Refs #<番号>`）。

実装PRの本文には、作成時から `Closes #<番号>` を書く。判断待ちで Draft のあいだも `Refs` にしない。実装PRは Issue 1つにつき1つで、判断待ちが残るあいだは Draft のままマージされないため、マージされる時点では Issue は完了している。`Refs` で作ると Ready にするときに書き換え忘れ、マージ後も Issue が残る。

## 出力形式

終わりに、PRのURLと、UATで参考にする受け入れ基準（設計文書の該当箇所）を示す。判断待ちがあれば、Draft PRと質問コメントのURL、仮案で実装・検証した範囲と未確認事項を示す。

## 他のスキルとの関係

| スキル | 使う場面 |
| :--- | :--- |
| `test-as-tdd` | テストと実装 |
| `test-code` | 品質ゲート |
| `design-docs` | 不足・未決事項の仮案作成、実装中に分かったことの反映、回答後の設計文書の修正 |
| `create-pullrequest` | 実装PRの作成と本文の更新 |

**User:** （PRコメントで「既存のまま残す」と回答してから）/implement-design 44

**Agent:** 既存の実装PRへの回答を反映し、「既存のまま残す」を確定仕様として設計文書とPR本文を更新しました。実装・テストとの整合と品質ゲートを確認し、Ready for review にしました。URL: ... UATでは `specification.md` の業務ルール「馬番の取り込み」を参考にご確認ください。
